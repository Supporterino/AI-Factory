# ADR-0029: CI and release automation

**Context.** Audit D4 found no CI: `dist/` is gitignored, the committed plugin bundle can drift, and publishing was a manual `npm publish`. The package is not on npm yet, so trusted publishing cannot be configured until after the first release. The CLI version lives in `package.json` and `src/version.ts`, the changelog is curated by hand, and ADR-0022 asks for an install snapshot per release.

**Decision.**
- **CI.** GitHub Actions runs on pull requests, pushes to `main` and manually. The full suite runs on `ubuntu-24.04` and `macos-latest` because the macOS sandbox is part of the enforcement layer. Both jobs use Node 24 and the Bun version in `packageManager`, install with `--frozen-lockfile`, then run lint, typecheck, tests, build and a check that the committed plugin bundle is current. A separate job packs the npm tarball, installs it and runs the binary. A Node 20.3/22/24 matrix smoke-tests the built bundle, covering the `engines` floor. The changeset check on PRs is advisory, not blocking.
- **Versioning.** Changesets 3.0.3 owns version bumps and changelog generation. Every user-facing change adds a `.changeset/*.md` fragment. The maintainer runs `bun run release:version` on a `release/vX.Y.Z` branch; it runs `changeset version`, syncs `src/version.ts` and regenerates `test/fixtures/install-<version>.json`. The resulting version PR is a normal PR, so CI runs without a GitHub App or PAT. No Changesets bot PR is used.
- **Publishing.** The release workflow runs on every push to `main` and manually. It checks whether the current `package.json` version is already on npm and whether the GitHub Release exists. If either is missing, it runs the full check on Ubuntu, packs the tarball and, after the `npm` environment approval, publishes only an unpublished version with `npm publish --provenance --access public`. It then creates the `X.Y.Z` tag (no `v` prefix) and GitHub Release from the CHANGELOG section and attaches the tarball. The workflow is idempotent, so a failed release can be re-run. Changesets' own `changeset publish` would create `vX.Y.Z` tags; this repository does not use that command.
- **Authentication.** The first publish is manual (`npm login` plus `npm publish`) because npm cannot configure a trusted publisher for a package that does not exist. After that, the package is configured for GitHub Actions trusted publishing with workflow `release.yml` and environment `npm`, and the trusted publisher must explicitly allow direct `npm publish` (the default after September 2026 allows stage publishing only). No `NPM_TOKEN` is stored in the repository. Publishing is additionally gated by the repository variable `RELEASE_ENABLED=true`, so the first merge cannot attempt an unconfigured publish; set it after the manual publish and trusted-publisher setup. `package.json` `repository.url` must exactly match the GitHub repository, or npm rejects the provenance/publish.
- **E2E.** The real-opencode test is a manual workflow. It installs the pinned `@opencode/cli@2.1.2` and runs the stub-model runtime test; it is not part of PR CI.

**Consequences.**
- Release tooling needs Node 24 because Changesets 3 requires it. The published CLI still supports Node >=20.3; the Node 20.3 smoke job enforces that.
- Merging a version PR can publish. `main` must require pull requests and the CI checks, and the `npm` environment should require a reviewer. Protecting release tags (`X.Y.Z`) against deletion or update is also required.
- The release job runs the suite again on `main`; this is deliberate because a tag/release must be proven against the exact commit that is published.
- The first release needs a short manual sequence: publish 0.2.0, configure the trusted publisher, set `RELEASE_ENABLED=true`, then run the release workflow for 0.2.0. After that, merging a version PR publishes. The manual 0.2.0 upload has no provenance attestation; releases published by the workflow do.
- The changelog format changes from 0.2.1 onward: Changesets generates `### Major/Minor/Patch Changes` sections. The 0.2.0 section stays as written.
- The Linux CI run is the portability check. macOS-only sandbox tests still skip on Ubuntu, so both runners are required.
